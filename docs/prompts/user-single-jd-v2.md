## 2. Anti-AI Linguistic Rules (去 AI 味死命令 — 违反任意一条即视为失败)
* **禁令 1【严禁同义词复读】**：在写 `对象` 和 `行动` 时，绝对不准照抄 JD 原文的名词！必须把抽象名词还原成**打工人电脑屏幕上的具体物件**（例如：不要写“对象：机评输出与人工标注”，要写“飞书/腾讯文档里那张几百行的 Badcase 对照表、Auto-eval 评分提示词、以及外包标注员打架的争议样本”）。
* **禁令 2【严禁机械免责尾巴】**：彻底删掉“并非招聘方已经答复，也不是访谈记录”、“不把相关当因果”、“不把点击直接当成用户满意”、“范围待确认：JD 未说明范围”这类像机器人免责声明一样的废话！如果某件事需要求职者去面试确认，直接用自然的人话写：“这事 JD 里没交底，得进面问清楚是让你只写规则，还是直接上手改工作流。”
* **禁令 3【举例必须带真实 Query，禁用“假设……”开头】**：在写 `举例` 时，严禁用“假设一条规则……”、“假设同题检索材料……”这种干瘪的填空句！必须直接给出一个**带具体用户搜索词（Query）或具体业务故障的微缩现场**（如：“用户搜‘2026北京落户积分怎么算’，结果答案漏了社保年限要求……”）。
* **禁令 4【去掉翻译腔与公文连词】**：禁用“推进相关同学处理”、“使评估可重复”、“可获得的 case 证据”等生硬表达。改成大厂日常口语：“拉着算法对齐”、“把人工盯盘变成跑脚本”、“手头能抓到的报错日志”。
* **禁令 5【社会学分析要见血】**：底部的 `社会学分析` 绝不能写成软绵绵的职责总结。必须结合劳动过程理论（如：隐性知识的编码化、算法流水线上的“人工校准工”、有责无权的跨部门推进），一针见血地指出这个岗位在组织分工里的真实生态位。

### [Output]

#### 01 把人工评测标准写成自动运行的脚本工具
* **原文**：与 WorkBuddy 等 Agent 工具以及算法同学协作，将评估流程沉淀为可运行的 skill / agent，并通过消融实验迭代判定逻辑
* **对象**：原本散落在飞书/腾讯文档里的评判标准（Rubrics）、WorkBuddy 等内部 Agent 编排画布、以及成百上千条待测的搜索问答样本。
* **行动**：把以前靠人眼一条条看的“好答案标准”，拆成大模型能听懂的分步指令（Prompt 节点 + 代码校验），搭成一套点一下就能自动跑分的工作流；每次改完评判规则，故意关掉其中一两个条件重跑一遍，看哪些题的得分变了。
* **用途**：每次算法发新版本，总不能全靠人力熬夜重测一遍；做成自动工作流是为了随时一键跑分，同时搞清楚到底哪条规则在真正起作用、哪条规则是废话。
* **举例**：在测微信搜一搜的“医疗问答”时，你在自动评测 Agent 里加了一条新规：“没标三甲医院出处的答案一律扣分”。为了验证这条规则好不好使，你拿同一批 200 道题，分别在“开启”和“关闭”这条规则下各跑一次，挑出那 18 条原本及格、现在被判不及格的题，逐条看是不是真的抓准了野鸡信源。
* **交付**：一套在内部平台上能直接跑通的评测 Agent 节点流，外加一张“规则改动前后的判分翻转对比表”。
* **做得好**：平庸的做法是写一堆笼统的评语让大模型自己打分，结果每次重跑分数都乱飘；高手的做法是把判断逻辑拆成“先抽事实点、再比对信源、最后合分”的确定性步骤，哪道题判错了，一眼就能顺着节点揪出是哪条规则卡得太死。
* **这项里的词**：
  * **skill / agent**：在这里不是让你从头开发一个面向C端用户的聊天机器人，而是用公司内部现成的工作流工具（如 WorkBuddy），把“怎么给搜索答案打分”串成一套自动干活的脚本。具体是只做离线打分工具，还是会接进线上实时拦截链路，进面时可以顺嘴问一句。
  * **消融实验（Ablation）**：原本是算法调模型用的词，放在这里其实就是“控制变量测试”——每次只改或关掉一条打分规则，看同一批测试题里有哪些结果变了，防止你改了半天规则其实全靠蒙。

#### 02 抓出机器打分和人工打分“打架”的原因
* **原文**：推进机评与人工标注对齐，分析一致率、归因 badcase，并下钻到具体 case
* **对象**：大模型自动打出来的分数（机评）、人工标注团队打的分数（人评），以及两边打分不一致的争议题（Badcase）。
* **行动**：拉一张表算出机器和人打分有多大比例能对上（一致率）；把两边吵得最凶的错题拎出来，逐条扒开看——到底是给机器写的打分提示词太模糊，还是人工标注员自己都没看懂标准乱打钩。
* **用途**：机器打分虽然快，但如果跟人的真实体感差太多，算法团队根本不敢信你的评测报告；只有把两边的尺子校准到八九不离十，机评才能真正替掉人工。
* **举例**：200 道“微信公众平台规则问答”跑下来，机器和人工的一致率只有 71%。你抽了 20 道打架的题逐条细看，发现其中 12 道是因为答案“答对了结论，但引用的公众号文章过期了”——标注文档里根本没规定这种算几分，导致标注员随心情给及格，而机器死板地全判了 0 分。
* **交付**：一份《机评-人评一致率周报与分歧归因表》，里面明确标出：几成需要改机评 Prompt、几成需要更新人工标注手册并拉标注队长重训。
* **做得好**：新手一看到机评和人评不一致，就只会埋头改机评 Prompt 去迁就人工；老手会双向审视，敢于拿具体 Case 指出“这批人工标签本身就标错了”，顺手把标注指南里的模糊地带补齐。

#### 03 顺着错题排查是“没搜出来”还是“大模型瞎编”
* **原文**：关注 RAG 等影响最终答案效果的环节
* **对象**：用户搜的具体问题（Query）、搜索引擎召回的几篇公众号/网页切片（Chunks），以及大模型最后拼出来的总结答案。
* **行动**：看到一条烂答案时，不急着怪大模型“笨”，而是打开后台链路日志，一步步核对：是第一步搜出来的文章就不对？还是文章虽然搜对了，但关键段落被截断了？又或者是材料全齐，单纯是大模型自己总结歪了？
* **用途**：帮算法和工程同学精准分锅。如果问题出在底层搜索没召回好文章，你让大模型团队怎么调 Prompt 也是白费力气。
* **举例**：用户搜“深圳新能源车补贴申请截止时间”，AI 回答得特别流畅，但把去年的截止日期当成了今年的。你点开后台 RAG 召回日志一看，排在前三名的参考文章全都是 2024 年的旧推文，2026 年的新政根本没被搜出来——这时候你直接在工单上标“检索时效性缺失”，转给做搜索召回的算法同学，而不是让生成组去改模型。
* **交付**：一份带后台截图证据的《Badcase 链路归因清单》（按“检索漏召回 / 排序错位 / 上下文截断 / 生成幻觉”四类分好锅）。
* **做得好**：每抛出一个问题，都能附上具体的 Query 和检索切片证据；遇到后台日志没吐全、看不清中间状态的题，老老实实标上“需算法补打日志”，绝不靠脑补乱指方向。

#### 04 盯着算法把问题改掉，并用真实用户反应反推评分标准
* **原文**：推动评估发现的问题落地优化，并结合线上实验与真实用户行为校准评估体系
* **对象**：你整理出来的重点高频缺陷工单、线上 A/B 实验的核心指标（点赞、复制、追问、跳出率），以及你手头那套离线打分规则。
* **行动**：拿着归因好的错题集去跟搜索、算法同学排期修 Bug；等新版本上线跑 A/B 实验时，回头看一眼：那些被你的离线打分规则夸上天的答案，真实微信用户到底买不买账？如果不买账，反过来修改你的打分规则。
* **用途**：防止评测体系变成“自嗨”——有时候评测规则喜欢长篇大论的答案，但微信里搜东西的用户其实只想一眼看到结果然后复制走人。
* **举例**：你们原来的打分规则要求“答案必须分点列出背景、过程和结论”，谁写得全谁分高。但上线跑实验后发现，查“快递停运时间”的用户看到长篇大论直接划走了，反而是只有一句话加一张表的短答案被疯狂转发。你据此把离线评测规则改成了“工具查询类问题，首屏不直接给结论的倒扣分”。
* **交付**：一张《高频缺陷修复追踪表（含对接人与上线状态）》，外加一份《基于线上用户反馈的评测标准校准说明》。
* **做得好**：不仅能把问题推上线，还能敏锐抓到“离线高分、线上遇冷”的倒挂现象，用真实的用户行为数据说服团队改掉教条的评测红线。

#### 能力与准备
* **明确要求 · 大厂评测/标注实战经验**：第一条写死了“必选项”。面试官没工夫从零教你什么是 Rubrics 和一致率，你简历里必须直接亮出你在上一家大厂写过多少维度的评分标准、处理过多少条 RAG/Agent 错题。
* **明确要求 · 把流程做成自动化工具的手感**：不能只会写静态 Word 文档，得展示你用 Coze、Dify 或内部平台把一串 Prompt 串成自动批处理工作流的实操经验。
* **明确要求 · 死磕烂 Case 的耐性与跨部门沟通**：这活有近一半时间在看枯燥的错题表和跟算法对线，既要坐得住冷板凳看几百条日志，又要能用算法听得懂的语言（召回率、幻觉率、分布偏移）把问题推下去。
* **待确认 · 四个方向是全包还是单点切入**：JD 列了“机评、Rubrics、RAG、Agent 评测”四块，面试时看自己过往最熟哪一块，主攻一点讲透即可。

**可以准备的材料**
1. **一页《搜索问答评测与机评拆解实例》（脱敏版）**：挑 5 个真实的微信搜一搜复杂问题（比如政策、医疗、旅游攻略），写出你的 3 档评分标准，并画一张草图展示怎么把它拆成 Agent 的 3 个自动判断节点。
2. **一张《RAG 错题归因复盘表》**：展示你是怎么把“答非所问”拆解成“检索没捞着”、“捞着了但排太后”和“模型自己看走眼”这三类具体原因的。

**面试可以练什么**
* **追问 1**：「给你 100 条搜索问答，现在大模型自动打分和人工打分的一致率只有 70%，你第一步干嘛？怎么决定是改机评 Prompt 还是找标注团队算账？」
  * *内行答法*：别上来就说改模型。先拉一张交叉混淆矩阵，看分歧集中在哪个分数段；然后抽 15 条分歧最大的题人工盲审——如果连你自己看这 15 条题都拿不准该给几分，说明是评分标准（Rubrics）本身写得太模糊，先改标准；如果标准极其清晰、人工标错了，找标注方返工；如果人工全对、机器死板报错，再拆解机评 Prompt 或加消融实验。
* **追问 2**：「离线评测跑分涨了 8%，但上线跑 A/B 实验发现微信用户的满意度反而跌了，你会怎么排查？」
  * *内行答法*：这是典型的“评测标准失真”。从两个切口查：一是看测试集（Benchmark）里的题是不是太老了，跟线上真实用户最近搜的热点分布不一致；二是把线上用户秒退或点踩的题捞出来，看看是不是离线规则过度奖励了“长篇大论、滴水不漏但极度啰嗦”的公文式回答。

#### 社会学分析
* **卡片摘要**：
  这份工作表面上是在训练 AI，实质上是在做**“人类常识的代码化”**——把模糊的好坏判断拆解成机器可执行的流水线标尺，并替算法系统的边界失灵充当人工校准器。
* **展开完整分析**：
  在大模型时代，产品经理的职能正在发生一场静默的转移：从以前画原型图设计交互，变成了给黑盒模型制定“审判法典（Rubrics）”。通过编写评测 Agent、计算人机一致率与跑消融实验，组织实际上是在把原本依赖人类编辑直觉的“什么算好内容”，强行压平为一套可批量复制、可追责的量化指标。对于实习生而言，这里存在着微妙的张力：一方面，你像立法者一样参与定义机器的评判标准；但另一方面，当 RAG 检索与生成链路出现千奇百怪的幻觉时，你又必须化身数字流水线上的“质检员”，用肉眼一条条翻看报错日志，替尚未成熟的自动化系统填补最后一公里的缝隙。
